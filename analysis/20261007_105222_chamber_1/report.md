  - The captures show the host did look again but never actually tried to connect: 3/3 of these runs contain **zero** Create Connection commands after the loss. The sensor was still on the air in 1/3 runs, but only 0/3 saw a *connectable* advertisement from it, so the kernel's auto-connect path had nothing to act on. Duplicate filtering was enabled on the re-scan in 2/3 runs, so the low advertising-report counts in the tail are partly a filtering artefact and are **not** evidence that the sensor became unreachable.
  - Non-recovery is therefore a property of this driver/stack configuration as much as of the RF conditions, and these runs do not bound how long the outage would have lasted with retries enabled.

## Reconnected vs recovered data
A reconnect counts as recovered only if data followed it. `ttfs` = time from Connection Complete to the first ECG sample (Polar) or notification (others); `data back` = first data after the first loss; `data/conn. s` = samples (Polar) or notifications per second of post-loss connected time. Per-connection and per-loss detail, including when the sensor advertised (connectably) again: `tables/connections.csv`, `tables/losses.csv`.
